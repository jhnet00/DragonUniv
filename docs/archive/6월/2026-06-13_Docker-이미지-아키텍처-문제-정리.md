## 작업 배경

팀원이 Docker Hub에 올라간 Dragon University Frontend/Backend 이미지를 VM에서 사용하려고 했으나,
이미지 아키텍처가 VM 아키텍처와 맞지 않아 실행 또는 pull 문제가 발생했다.

처음에는 Apple Silicon Mac에서 빌드한 이미지가 `arm64`로 올라갔고,
팀원 VM은 `amd64(x86_64)` 환경일 가능성이 있어 실행 실패가 예상되었다.

이후 `amd64` 전용 이미지로 다시 빌드했지만, rb가 사용하는 `dragon-k3s` VM은 `aarch64(arm64)` 환경이라
이번에는 rb VM에서 `amd64` 전용 이미지를 pull할 수 없는 문제가 발생했다.

---

## 핵심 개념

Docker 이미지는 CPU 아키텍처별로 다르게 빌드될 수 있다.

| 표현 | 의미 |
|------|------|
| `amd64` | 일반적인 Intel/AMD 64비트 서버, Windows VM, x86_64 Ubuntu VM |
| `x86_64` | Linux에서 보이는 amd64 아키텍처 이름 |
| `arm64` | Apple Silicon Mac, ARM 서버/VM |
| `aarch64` | Linux에서 보이는 arm64 아키텍처 이름 |

즉 아래 두 표현은 같은 계열이다.

```txt
amd64  == x86_64
arm64  == aarch64
```

## 발생한 에러와 의미

### 1. `unknown flag: --platform`

VM에서 아래 명령을 실행했을 때 발생했다.

```bash
docker buildx build --platform linux/amd64 -t rubyjeenkim/dragon-frontend:latest --push ./Frontend
```

에러:

```txt
unknown flag: --platform
```

의미:

- 현재 Docker CLI가 `buildx` 또는 `--platform` 빌드 옵션을 제대로 지원하지 않는 상태
- 또는 Docker Desktop이 아닌 구버전 Docker 환경일 수 있음
- `--platform`을 쓰려면 Docker Desktop 또는 buildx가 설정된 Docker 환경이 필요함

### 2. `zsh: command not found: docker`

Mac 터미널에서 Docker 명령을 실행했을 때 발생했다.

```txt
zsh: command not found: docker
```

의미:

- Mac에 Docker Desktop 또는 Docker CLI가 설치되어 있지 않음
- Docker Desktop 설치 후 앱을 실행하고 새 터미널을 열어야 함

확인 명령:

```bash
docker --version
docker buildx version
```

### 3. `no matching manifest for linux/arm64/v8`

`amd64` 전용 이미지를 올린 뒤, rb의 `arm64` VM에서 pull할 때 발생했다.

```bash
docker pull rubyjeenkim/dragon-frontend:latest
```

에러:

```txt
no matching manifest for linux/arm64/v8 in the manifest list entries
```

의미:

- 현재 VM은 `linux/arm64/v8` 이미지를 원함
- Docker Hub의 `latest` 태그에는 `amd64` 이미지만 있음
- 따라서 ARM64 VM에서는 해당 이미지를 받을 수 없음

---

## 확인한 명령

VM 아키텍처 확인:

```bash
uname -m
```

rb의 `dragon-k3s` VM 결과:

```txt
aarch64
```

의미:

- rb의 VM은 ARM64 환경
- 이 VM에서 일반 `docker build`를 하면 `arm64` 이미지가 만들어짐
- 팀원 VM이 `amd64`라면 이 이미지가 실행되지 않을 수 있음

Docker 이미지 아키텍처 확인:

```bash
docker inspect rubyjeenkim/dragon-frontend:latest | grep Architecture
docker inspect rubyjeenkim/dragon-backend:latest | grep Architecture
```

단, 멀티 아키텍처 이미지는 실행 환경에 맞는 이미지를 pull한 뒤 inspect해야 해당 로컬 이미지의 아키텍처가 보인다.

## 최종 해결 방향

rb의 VM은 `arm64`, 팀원 VM은 `amd64`일 수 있으므로,
한쪽 아키텍처만 지원하는 이미지보다 멀티 아키텍처 이미지로 Docker Hub에 push하는 것이 가장 안정적이다.

Mac에 Docker Desktop을 설치한 뒤 프로젝트 루트에서 실행:

```bash
cd /Users/rubykim/Desktop/dev/dragon-univ

docker buildx build --platform linux/amd64,linux/arm64 -t rubyjeenkim/dragon-frontend:latest --push ./Frontend
docker buildx build --platform linux/amd64,linux/arm64 -t rubyjeenkim/dragon-backend:latest --push ./Backend
```

이렇게 하면 같은 `latest` 태그 안에 두 아키텍처 이미지가 함께 들어간다.

```txt
amd64 VM  -> amd64 이미지 자동 pull
arm64 VM  -> arm64 이미지 자동 pull
```

## 상황별 빌드 방법

### Apple Silicon Mac에서 빌드

Docker Desktop 설치 후 buildx 사용:

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t rubyjeenkim/dragon-frontend:latest --push ./Frontend
docker buildx build --platform linux/amd64,linux/arm64 -t rubyjeenkim/dragon-backend:latest --push ./Backend
```

### amd64 VM에서 빌드

`uname -m` 결과가 `x86_64`이면 일반 빌드도 amd64 이미지가 된다.

```bash
docker build -t rubyjeenkim/dragon-frontend:latest ./Frontend
docker build -t rubyjeenkim/dragon-backend:latest ./Backend

docker push rubyjeenkim/dragon-frontend:latest
docker push rubyjeenkim/dragon-backend:latest
```

단, 이 방식은 기본적으로 `amd64` 전용 이미지가 되므로 ARM64 VM에서도 쓰려면 멀티 아키텍처 buildx가 더 좋다.

### arm64 VM에서 빌드

`uname -m` 결과가 `aarch64`이면 일반 빌드는 arm64 이미지가 된다.

```txt
aarch64
```

이 환경에서 일반 `docker build`만 하면 amd64 팀원 VM 문제를 해결할 수 없다.

## SSH 접속 메모

VM 접속 기본 형식:

```bash
ssh 사용자명@서버IP
```

예시:

```bash
ssh ruby@192.168.0.10
```

포트가 기본 22번이 아니면:

```bash
ssh ruby@서버IP -p 포트번호
```

## VM 안 프로젝트 경로 찾기

프로젝트 경로를 잊었을 때 사용한 방식:

```bash
find /root /home -maxdepth 4 -type d -iname "*dragon*" 2>/dev/null
```

오늘 확인한 경로:

```txt
/home/ruby/dragon-univ-fresh
```

이동:

```bash
cd /home/ruby/dragon-univ-fresh
```

## 후속 과제

- 팀원 VM에서 `docker pull rubyjeenkim/dragon-frontend:latest` 성공 여부 확인
- 팀원 VM에서 `docker pull rubyjeenkim/dragon-backend:latest` 성공 여부 확인
- k3s Pod 재시작 후 Frontend/Backend 정상 실행 확인
- 가능하면 `latest` 외에 날짜 또는 버전 태그도 함께 사용 검토
